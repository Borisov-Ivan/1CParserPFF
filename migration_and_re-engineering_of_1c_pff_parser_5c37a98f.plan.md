# План миграции и перепроектирования парсера 1C PFF

## 1. Сбор информации (PavDO -> 1CParserPFF)

- Экспорт текущих скриптов: `1CParserPFF_UI/pff_parser.py`, `pff_parser_gui.py`.
- Экспорт документации: `README.md`, и поиск файлов "ТЗ Парсер.md", "Идеальный формат отчёта.md" (если существуют в `docs/` или корне).
- Инициализация нового репозитория `C:\GitHub\1CParserPFF`.
- Создание структуры проекта:
  - `src/` (исходный код парсера)
  - `docs/` (спецификации форматов)
  - `tests/` (эталонные замеры)
  - `tools/` (скрипты анализа)

## 2. Создание эталонного замера (Reference Benchmark)

Вам нужно создать конфигурацию 1С, которая генерирует PFF, покрывающий все сложные кейсы.
**Рекомендации по составу конфигурации:**

1. **Общий модуль (Клиент/Сервер):**
  - Процедура, вызываемая с клиента.
    - Процедура, вызываемая с сервера.
    - Передача управления Клиент -> Сервер -> Клиент (если возможно, через возврат значения).
2. **Фоновое задание:**
  - Запуск фонового задания, которое делает вычисления и пишет в журнал регистрации (или просто "спит").
    - Это проверит, как PFF пишет `Context` для фоновых (обычно это Сервер, но отдельный сеанс).
3. **Ошибки:**
  - Код, вызывающий исключение (`ВызватьИсключение`) внутри `Попытка-Исключение` и без обработки.
4. **Внешняя компонента (опционально):**
  - Если есть возможность, вызов метода внешней компоненты (как в вашем примере с Hash), чтобы проверить флаги `ОбработкаСервером`.
5. **Транзакция:**
  - Явная транзакция (`НачатьТранзакцию`), чтобы увидеть, как это отражается в PFF (если вообще отражается).

**Действия:**

- Вы создаете конфигурацию и запускаете сценарий.
- Вы присылаете полученный `.pff` файл (или его текстовое представление, если он бинарный, но обычно это текст в `{...}`).

## 3. Reverse Engineering (Исследование формата)

- Анализ эталонного PFF.
- Сопоставление строк PFF с исходным кодом 1С.
- **Главная цель:** Точно определить значение каждого поля в записи PFF (особенно последние числовые флаги `0,1,0` и т.д.).
- Документирование формата в `docs/PFF_Specification.md`.

## 4. Проектирование целевых форматов (Target Specs)

Разработка форматов, оптимизированных для LLM (token-efficient, context-rich).

- **TRACE (Поток выполнения):**
  - Хронологический лог.
  - Явные маркеры переключения контекста `[CLIENT]`, `[SERVER]`, `[BG_JOB]`.
  - Умное сжатие (не повторять имя модуля, если оно не изменилось).
  - Обработка вложенности (отступы).
- **PERF (Производительность):**
  - Дерево вызовов (Call Tree) с агрегацией времени.
  - Hotspots (Топ методов по "чистому" времени).
  - Связь с TRACE (ссылки на ID событий).

## 5. Реализация нового парсера (v2.0)

- Разработка ядра на Python (без GUI пока).
- Реализация потокового чтения (для больших файлов).
- Корректный маппинг полей (исправление ошибки с `Context`).
- Корректный подсчет времени (учет вложенности и параллельности).

## 6. Тестирование

- Прогон эталонного замера через новый парсер.
- Сравнение выходного TRACE с ожидаемой логикой.
- Верификация PERF отчета.
