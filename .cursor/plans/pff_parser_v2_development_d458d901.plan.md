# План разработки парсера PFF v2.0

## Контекст и вводные

1. **Размер данных:** Средний размер замера до 10 Мб. Это позволяет использовать **In-Memory** архитектуру (загрузка всех событий в память) без сложных потоковых оптимизаций или промежуточных БД.
2. **Конфигурация vs Расширения:** Критически важно визуально разделять код, выполняемый в основной конфигурации, и код в расширениях.
3. **Детализация:** Необходимо сохранять по-строчную разбивку для точного анализа производительности (PERF), даже для последовательных строк (так как время замеряется для каждой). Группировка строк возможна только если они имеют ничтожно малое время выполнения, но на первом этапе сохраняем полную детализацию.
4. **Тестовые данные:** Используется реальный замер `reference.pff`, полученный из тестовой обработки.

## Фаза 1: Спецификация исходного формата PFF

**Файл:** `docs/PFF_Format.md`

Задокументировать структуру `reference.pff`, уделив особое внимание полям идентификации кода:

- **Сигнатура записи:**
  - `ExtGUID` (поле 5): GUID расширения (или пустой для основной конфигурации).
  - `ExtName` (поле 13): Имя расширения (строка).
  - `ExtMethodType` (поле 6): Тип перехвата (0=нет, 4=Вместо, и др.).
- **Остальные поля:** GUID модуля, ObjectType, Флаги контекста (Клиент/Сервер).

## Фаза 2: Алгоритм восстановления стека вызовов

**Файл:** `docs/CallStack_Algorithm.md`

Алгоритм (In-Memory):

1. **Загрузка:** Читаем весь PFF в список объектов Python.
2. **Группировка:** Сортируем/индексируем записи по `ModuleGUID` (или Имени) + `Extension`.
3. **Построение дерева:**
  - Используем эвристику `Total > Pure` для определения узлов с потомками.
  - Ищем потомков среди записей, хронологически (в рамках логики 1С) подходящих под вызов.
  - Учитываем переходы между Расширением и Основной конфигурацией (часто расширение вызывает `ПродолжитьВызов` или замещает метод).
4. **Связывание:** Объединяем клиентский и серверный потоки.

## Фаза 3: Спецификация целевого формата

**Файл:** `docs/Target_Format.md`

### Принципы

- **Явное указание Расширения:** Если код выполняется в расширении, это должно быть видно в каждой строке (или в заголовке блока модуля).
- **Строки:** Оставляем каждую строку отдельной записью (для точности `Pure` времени).

### TRACE формат

```text
[C] L0 [Ext:MyExtension] Обр.Тест.Форма:29 | Сообщить("В расширении")
[C] L0 :30 | ПродолжитьВызов()
[C]   L1 Обр.Тест.Форма:29 | Сообщить("В основной")
```

- Добавить префикс `[Ext:Name]` или `[Conf]` (для основной, можно опускать по умолчанию).
- Формат должен позволять LLM четко понимать, чей код выполняется.
