# Документация 1CParserPFF

Для быстрого старта и понимания назначения инструмента см. [README.md](../README.md).

## 1. Входной формат: PFF

### Что такое PFF и откуда его взять

**Создание замера в 1С:**

1.  **Платформа:** Меню **Отладка → Замер производительности**.
    -   Нажмите кнопку "Включить замер".
    -   Выполните операцию в 1С (проведение документа, открытие формы и т.д.).
    -   Нажмите кнопку "Выключить замер".
    -   Откроется окно с результатами. Нажмите кнопку "Сохранить" (дискета) и выберите формат `.pff`.

2.  **Конфигурация (Управляемые формы):**
    -   Откройте форму **"Анализ замеров"** (обычно в разделе "Администрирование" или "Инструменты разработчика").
    -   Нажмите "Начать замер".
    -   Выполните действия.
    -   Нажмите "Завершить замер" и сохраните файл.

**Формат файла:**
Текстовый файл с вложенными структурами (похож на JSON, но без строгого синтаксиса). Содержит хронологию событий выполнения кода 1С.

Каждое событие содержит:
-   `Module` — полное имя модуля (например, `ОбщийМодуль.ОбщегоНазначения`)
-   `Line` — номер строки в модуле
-   `Code` — текст строки кода (если доступен)
-   `Total` — общее время выполнения строки (включая вложенные вызовы)
-   `Pure` — чистое время выполнения (без вложенных вызовов)
-   Контекст: Клиент / Сервер / Вызов сервера

**Поддерживаемые варианты PFF:**
Парсер автоматически определяет формат (версии платформы 8.2, 8.3, разные режимы записи). Вам не нужно разбираться в технических отличиях — просто подайте файл на вход.

**Примеры файлов:**
-   [examples/Проверка расчета хэша.pff](../examples/Проверка расчета хэша.pff)
-   [tests/reference.pff](../tests/reference.pff)

## 2. Выходные форматы отчётов

### 2.1. TRACE — анализ сценария выполнения

**Назначение:** Понять **что происходило** (логика, последовательность вызовов, причинно-следственные связи).

**Две детализации:**
-   **compact** (обзорный) — только ключевые вызовы, структурный шум (циклы, условия) отсечён. Для быстрого понимания сценария. **Рекомендуется для начала.**
-   **full** (подробный) — полная трассировка с деталями (построчное выполнение в каждом модуле). Для глубокого анализа или верификации.

**Структура отчёта TRACE:**

1.  **СВОДКА** — общая информация о замере (количество событий, сессии, общее время).
2.  **TRACE META** — метаданные отчёта (формат, детализация, сессии).
3.  **TRACE COVERAGE** — статистика покрытия: сколько событий включено, сколько скрыто (и почему: структурный шум, мелкие операции, порог).
4.  **MODULES MAP** — таблица соответствия алиасов модулям.
    ```
    M01: [X1] Обработка.НастройкаПрограммы.Форма.НастройкиЭП.Форма
    M02: [X1] ОМ.ргСервисКриптографииCryptoAPI
    M04: ОМ.ОбщегоНазначения
    X1: ргОблачныеПодписиKonturCryptoAPI (расширение)
    ```
    *Зачем: сокращение повторяющихся имён модулей для экономии места и читаемости.*

5.  **EXECUTION FLOW** — главная секция: **хронологическое дерево вызовов**.

    **Формат строки:**
    ```
    ?1354 [S] M01:47 | Хеш = ргСервисКриптографииCryptoAPI.ВычислитьХешГОСТ2012(...);
    ```

    **Расшифровка:**
    -   `?1354` — ссылка на событие с ID 1354 в исходном замере. `?` = INFERRED (эвристическая связь), `#` = FACT (подтверждённый факт).
    -   `[S]` — контекст выполнения: `[C]` клиент, `[S]` сервер, `[C→S]` вызов сервера с клиента.
    -   `M01:47` — модуль M01 (см. MODULES MAP), строка 47.
    -   `| ...` — текст строки кода.

    **Отступы = вложенность вызовов:** дочерние вызовы сдвинуты вправо.

    **Пример из практики 1С:**
    ```
    ?1534 [C→S] M01:32 | Результат = ПроверитьПолучениеХэшаНаСервере();
      ?1354 [S] M01:47 | Хеш = ВычислитьХешГОСТ2012(ДвоичныеДанные);
        ?1303 [S] M02:4363 | ОбъектКомпоненты = ОбъектВнешнейКомпоненты();
          ?761 [S] M04:6468 | РезультатПроверки = ПроверитьПодключениеКомпоненты();
          ?110 [S] M07:92 | Результат = Запрос.Выполнить();
    ```
    *Что видно: клиент вызвал сервер (строка 32) → сервер запустил вычисление хэша → потребовалась внешняя компонента → проверка подключения → запрос к БД.*

6.  **CALL INDEX** — краткий индекс главных вызовов (навигация).
7.  **MODULES** — детализация по модулям (построчно с кодом и временем). В режиме compact — только ключевые строки.
8.  **TRACE REPRODUCE** — команда для воспроизведения отчёта.

**Примеры полных отчётов:**
-   [examples/Проверка расчета хэша_TRACE_COMPACT.txt](../examples/Проверка расчета хэша_TRACE_COMPACT.txt)
-   [examples/Проверка расчета хэша_TRACE_FULL.txt](../examples/Проверка расчета хэша_TRACE_FULL.txt)

### 2.2. PERF — анализ производительности

**Назначение:** Найти **где тормозит** (узкие места, горячие точки).

**Основной параметр: порог (threshold)** — минимальное время операции в миллисекундах для включения в отчёт. Например, `--threshold 10` покажет только операции длительнее 10 мс.

**Структура отчёта PERF:**

1.  **СВОДКА** — общая статистика.
2.  **CRITICAL PATH** — критический путь (самые долгие операции в порядке выполнения).
3.  **HOTSPOTS** — горячие точки (топ операций по чистому времени `Pure`).
4.  Построчная детализация по модулям с указанием времени.

**Типичные паттерны в PERF:**
-   **Медленный запрос:** `Запрос.Выполнить()` — время 1500 мс → смотрим строку, оптимизируем индексы/запрос.
-   **HTTP-вызов:** `HTTPСоединение.Получить()` — время 800 мс → смотрим, можно ли кешировать, уменьшить объём.
-   **Внешняя компонента:** `AddIn.MethodCall()` — время 300 мс → анализируем необходимость/альтернативы.

**Пример фрагмента PERF:**
```
=== HOTSPOTS ===
1. [S] M04:6468 | Запрос.Выполнить() — Pure: 1523 мс
2. [S] M05:145 | HTTPСоединение.Получить(...) — Pure: 845 мс
3. [C→S] M01:32 | ПроверитьПолучениеХэшаНаСервере() — Total: 2100 мс (Pure: 12 мс)
```

## 3. Парсер: режимы и опции

### 3.1. Когда какой режим использовать

| Вопрос | Режим | Детализация/порог |
| :--- | :--- | :--- |
| Что вызывалось и в каком порядке? | TRACE | compact |
| Откуда идёт вызов функции X? | TRACE | compact → найти функцию в EXECUTION FLOW |
| Почему так долго выполняется операция? | PERF | порог 5-10 мс |
| Какие запросы выполнялись? | TRACE | full (или compact, если видны в основной цепочке) |
| Нужна полная детализация для верификации | TRACE | full |
| Подготовить данные для ИИ-анализа | TRACE | compact (меньше токенов) |

### 3.2. CLI (для автоматизации)

**Формат команды:**
```bash
python src/pff_parser.py <входной.pff> [выходной.txt] [опции]
```

**Основные опции:**
-   `--mode {TRACE,PERF}` — режим отчёта (по умолчанию TRACE).
-   `--trace-detail {full,compact}` — детализация TRACE (по умолчанию compact).
-   `--threshold N` — порог в миллисекундах для PERF (по умолчанию без фильтрации).
-   `--no-model-prompt` — не включать промпт для ИИ-модели в начало отчёта.
-   `--no-context` — не включать контекст выполнения `[C]`/`[S]` (устаревшая опция).

**Deprecated опции** (работают для обратной совместимости):
-   `--no-compact` — эквивалентно `--trace-detail full`.

**Формирование имени выходного файла** (если не указан):
-   TRACE: `<имя>_TRACE_COMPACT.txt` или `<имя>_TRACE_FULL.txt`
-   PERF: `<имя>_PERF.txt`

**Примеры:**
```bash
# TRACE compact
python src/pff_parser.py замер.pff

# TRACE full с явным именем выхода
python src/pff_parser.py замер.pff отчёт_подробный.txt --trace-detail full

# PERF с порогом 10 мс
python src/pff_parser.py замер.pff --mode PERF --threshold 10
```

### 3.3. GUI (основной способ для разработчиков 1С)

**Запуск:**
-   **EXE:** двойной клик на `1CParserPFF.exe` (не требует Python).
-   **Python:** `python src/pff_parser_gui.py` (из корня репозитория).

**Интерфейс:**
1.  **Выбор файла** — кнопка "Обзор", выбрать `.pff`.
2.  **Режим** — переключатель TRACE / PERF.
3.  **Для TRACE:** два радио-выбора — `Обзор (compact)` / `Подробный (full)`.
4.  **Для PERF:** поле "Порог (мс)" — минимальное время для включения в отчёт (можно оставить пустым).
5.  **Чекбокс "Промпт для модели"** — добавить в начало отчёта инструкции для ИИ (Claude/GPT) по интерпретации формата.
6.  **Кнопка "Сформировать отчёт"** — запуск парсинга, результат отобразится в текстовом поле.
7.  **Кнопки внизу:**
    -   "Сохранить в файл" — сохранить отчёт (имя предлагается автоматически).
    -   "Копировать в буфер" — скопировать текст отчёта.
    -   "Открыть папку" — открыть папку с сохранённым файлом.

**Особенности GUI:**
-   Параметры, не относящиеся к выбранному режиму, автоматически скрываются (например, "Порог" скрыт для TRACE).
-   При выборе файла путь запоминается для следующего запуска.

## 4. Интерпретация результатов (практические советы)

### Работа с TRACE

1.  **Начать с TRACE COVERAGE** — понять, сколько данных скрыто (если `hidden: threshold=1000`, значит 1000 мелких событий не показаны — это нормально).
2.  **Открыть MODULES MAP** — запомнить/найти нужные модули (например, M01 = форма, M04 = ОбщегоНазначения).
3.  **Читать EXECUTION FLOW сверху вниз** — это хронология. Отступы = вложенность.
4.  **Контекст `[C→S]`** — переход с клиента на сервер (важно для понимания, где сетевая задержка).
5.  **Если нужна детализация конкретного модуля** — смотреть секцию MODULES (там построчно с кодом).
6.  **Ссылки `#ID` и `?ID`** — для верификации можно вернуться к исходному замеру (событие с этим ID). `?` означает, что связь восстановлена эвристически (точность ~90%), `#` — факт из данных.

### Работа с PERF

1.  **HOTSPOTS** — смотреть первым. Топ самых медленных операций по чистому времени (`Pure`).
2.  **Найти строку кода** — каждая запись содержит модуль и номер строки → открыть конфигурацию → найти этот модуль → перейти на строку.
3.  **Анализ причин:**
    -   `Запрос.Выполнить()` — запрос к БД, проверить индексы/условия.
    -   `HTTPСоединение.*` — внешний вызов, проверить необходимость/кеширование.
    -   Обращения к внешним компонентам — оптимизация/замена.
4.  **CRITICAL PATH** — показывает, какие операции выполнялись последовательно и внесли основной вклад в общее время.

## 5. Примеры использования (из практики)

**Сценарий 1: Медленное проведение документа**
-   **Проблема:** Документ проводится 5 секунд.
-   **Действие:** Замер → PERF с порогом 10 мс.
-   **Результат:** HOTSPOTS показал запрос на строке 245 модуля `ДокументыСервер` (1520 мс).
-   **Решение:** Оптимизирован индекс в БД → время запроса упало до 80 мс.

**Сценарий 2: Непонятный серверный вызов**
-   **Проблема:** При нажатии кнопки происходит задержка, хотя код кнопки простой.
-   **Действие:** Замер → TRACE compact.
-   **Результат:** EXECUTION FLOW показал: Форма → Обработчик кнопки (строка 32) → Серверный вызов (строка 47) → Три вложенных вызова (показаны с отступами), один из которых — долгий пересчёт итогов.
-   **Решение:** Перенос пересчёта в фоновое задание.

**Сценарий 3: Лишние обращения к серверу**
-   **Проблема:** Открытие списка справочника тормозит.
-   **Действие:** Замер → TRACE compact.
-   **Результат:** Подсчитали метки `[C→S]` в отчёте — 12 штук подряд. Нашли цикл, в котором 10 раз вызывается `ПолучитьРеквизитыСервера()`.
-   **Решение:** Вынесли получение данных за цикл (один вызов) → осталось 2 вызова сервера.

## 6. Сборка EXE (для тех, кто хочет собрать сам)

Если вы хотите собрать `1CParserPFF.exe` самостоятельно из исходного кода:

**Требования:**
-   Python 3.7+
-   PyInstaller

**Команды сборки:**

```bash
pip install pyinstaller
python build/build.py
```

**Результат:**
Файл `dist/1CParserPFF.exe` — готовый к распространению файл (не требует Python на целевой машине).
