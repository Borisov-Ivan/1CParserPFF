## 1. О программе

**1CParserPFF** — инструмент для анализа файлов замеров производительности 1С (расширение `.pff`). Он преобразует сырые данные замера в структурированные текстовые отчёты, удобные для анализа разработчиком и LLM.

Программа написана на Python 3, использует tkinter. Внешние зависимости не требуются.

## 2. Быстрый старт (GUI)

1. Запустите `1CParserPFF.exe` или `python src/pff_parser_gui.py`.
2. Нажмите «…» в поле «Путь к файлу» и выберите файл замера (`.pff` или `.txt`).
3. Выберите режим: **Трассировка (TRACE)** — логика и поток вызовов; **Производительность (PERF)** — узкие места.
4. (Опционально) Настройте параметры (см. [Настройки GUI](#6-настройки-gui)).
5. Нажмите «Сформировать» или Enter.
6. Результат появится в текстовом поле и сохранится рядом с исходным файлом (`*_TRACE.txt` или `*_PERF.txt`).

## 3. Как получить PFF-файл в 1С

1. Меню **Сервис и настройки** → **Настройки** → **Замер производительности**.
2. Нажмите «Начать замер».
3. Выполните нужные действия (проведение, открытие формы и т.д.).
4. Нажмите «Остановить замер».
5. В окне результатов — «Сохранить…» → тип файла **PFF** → сохраните на диск.

## 4. Два режима работы

### TRACE — «Что произошло?»

Восстановление потока выполнения и отладка логики.

**Секции отчёта:**

- **EXECUTION FLOW** — дерево вызовов (эвристика ~90%), вложенность, свёртка колбэков (`ВыполнитьОбработкуОповещения` и т.п.).
- **CALL MAP** — строки с наибольшим Budget (время во вложенных вызовах) и ссылки `-> see:` на блоки в MODULES.
- **MODULES** — справочник модулей, группировка по контексту, свёртка тривиальных процедур, убраны `КонецЕсли`/`КонецЦикла`, схлопнуты повторы (`30× Реквизиты.Вставить(...)`).

### PERF — «Почему медленно?»

Поиск узких мест и оптимизация.

**Секции отчёта:**

- **TOP ISSUES** — топ проблем (HTTP, SQL, Бизнес-логика, Ресурсы, Колбэк) с цепочками вызовов. Генерируется для формата 2b/2c.
- **Дерево критического пути** — классическое дерево (только для формата 1 с полем Level).
- **HOTSPOTS** — топ строк по Self time.

## 5. Словарь терминов

| Термин | Значение |
|--------|----------|
| **Total** (мс) | Полное время строки, включая все вложенные вызовы |
| **Pure / Self** (мс) | Чистое время именно этой строки |
| **Budget** | `Total - Pure` — время во вложенных вызовах |
| `[C]` | Код на Клиенте |
| `[S]` | Код на Сервере |
| `[C→S]` | Вызов серверной процедуры с клиента |
| `[?]` | Контекст неизвестен |
| `[Ext:Имя]` | Код из Расширения |
| ★ | Узкое место (высокое Self) |
| `⤷ [колбэки ×N: ...]` | Свёрнутая цепочка колбэков |
| `[свёрнуто]` | Процедура ниже порога |
| **Count** | Количество выполнений строки |

## 6. Настройки GUI

- **Путь к файлу** — исходный `.pff` или `.txt`.
- **Режим** — TRACE или PERF.
- **Точка входа** — фильтр по `Модуль:Строка` или подстроке кода.
- **Порог (мс)** — минимальное Total для включения (только PERF; в TRACE порог всегда 0).
- **Разворачивать имена модулей** — полные имена или короткие M1, M2.
- **Умное сжатие** (только TRACE) — объединение переносов строк.
- **Промпт для модели** — блок инструкций для LLM в начале отчёта.

## 7. Командная строка (CLI)

```
python src/pff_parser.py [file] [output] [options]
```

**Аргументы:**

- `file` — путь к PFF (обязательный)
- `output` — путь к выходному файлу
- `--mode {TRACE,PERF}`
- `--threshold N` — порог в мс
- `--entry "Module:Line"` — точка входа
- `--main-block N` — только блок N (0, 1, 2…)
- `--no-compact`, `--no-context`, `--no-expand-modules`, `--no-model-prompt`

**Примеры:**

```bash
python src/pff_parser.py data/trace.pff
python src/pff_parser.py data/trace.pff --mode PERF --threshold 10
python src/pff_parser.py data/trace.pff --main-block 0
```

## 8. Формат PFF — техническая справка

Спецификация восстановлена методом реверс-инжиниринга на основе эталонного замера. Файл PFF — текстовая сериализация внутренних структур 1С (фигурные скобки, запятые).

### Общая структура

```
{Version, SessionCount, MeasurementGUID,
    SessionBlock1,
    SessionBlock2,
    ...
}
```

- `Version` — версия формата (обычно 5)
- `SessionCount` — количество сессионных блоков
- `MeasurementGUID` — идентификатор замера

### Сессионный блок (Session Block)

Описывает сеанс (Клиент, Сервер, фоновое задание).

```
{10, "WS-HQ-43FAC", "", 1563, "", 32, "", AppGUID, SessionGUID, ...}
```

- `0` — тип записи (10 = заголовок сеанса)
- `1` — имя хоста
- `3` — номер сеанса
- `5` — тип приложения: `2` — Сервер, `32` — Тонкий клиент, `64` — Сервер

За заголовком идёт блок записей.

### Блок записей (Record Block)

```
{0, 32, BlockGUID,
    Record1,
    Record2,
    ...
}
```

- `0` — тип (0 = блок данных)
- `1` — количество записей
- `2` — GUID блока

### Структура записи (Record)

Каждая запись — одна строка кода.

| Индекс | Имя | Описание |
|--------|-----|----------|
| 0 | Signature | Блок идентификации (см. ниже) |
| 1 | Module | Полное имя модуля |
| 2 | Line | Номер строки |
| 3 | Code | Текст строки |
| 4 | Count | Количество выполнений |
| 5 | TotalTime | Время с вложенными (сек) |
| 6 | PureTime | Чистое время (сек) |
| 7–8 | TotalPct, PurePct | Проценты |
| 9 | ClientFlag | 1 = Клиент |
| 10 | ServerFlag | 1 = Сервер |
| 11 | SrvProcFlag | 1 = Обработка сервером (вызов с клиента) |
| 12 | BlockGUID | Ссылка на блок |

**Signature (поле 0):** `{{"",0}, ModGUID, ConfGUID, ObjType, ExtGUID, ExtMethodType, Base64, "ExtName"}` — тип объекта, расширение, GUID модуля.

### Важные особенности

1. **Иерархия:** Записи идут плоским списком, сгруппированы по модулям, а не хронологически. Стек восстанавливается по `TotalTime` vs `PureTime` и связям между модулями.

2. **Контекст:** `(1,0,0)` → Клиент; `(0,1,0)` → Сервер; `(1,0,1)` → вызов сервера с клиента.

3. **Расширения:** Код расширений — по `ExtName` и `ExtGUID` в Signature.

4. **Границы процедур:** Обычно нет строк `Процедура Имя()` / `Функция Имя()`, но есть `КонецПроцедуры` / `КонецФункции`. Блоки идентифицируются как `Func/Proc (:X-Y)`.

> **Важно:** В форматах 2b/2c поле `Level` отсутствует (равно 0). Дерево вызовов восстанавливается эвристически.

## 9. Алгоритмы парсера

- **PFFStreamParser** — потоковый парсер, посимвольное чтение.
- **ProcedureGrouper** — группировка по модулям/контексту/расширениям, разбиение на блоки по маркерам `КонецПроцедуры` / `КонецФункции`.
- **CallMapBuilder** — анализ Budget (`Total - Pure`), поиск подходящих блоков по времени.
- **ExecutionFlowBuilder** — рекурсивная реконструкция дерева, свёртка колбэков.
- **IssueAnalyzer** — кластеризация hotspots, классификация (SQL, HTTP и т.д.), построение цепочек вызовов.

## 10. Ограничения и точность

- Восстановление дерева — эвристика, точность ~85–90%. При `Count > 1` точность ниже.
- **MODULES** — факты; **EXECUTION FLOW** и **TOP ISSUES** — гипотезы о связях.
