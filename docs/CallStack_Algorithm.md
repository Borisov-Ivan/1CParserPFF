# Принятый подход вместо восстановления стека (TRACE v3)

Документ фиксирует отказ от `CallTreeBuilder` и описывает текущую стратегию подготовки TRACE-отчета.

## Почему отказались от восстановления дерева

Алгоритмическая реконструкция стека из плоского PFF оказалась ненадежной на реальных замерах:

- неоднозначное сопоставление по времени (`Total - Pure`);
- динамические/косвенные вызовы в коде;
- чувствительность к стилю кода;
- высокий риск ложных связей при принятии решений по результатам анализа.

## Что используется сейчас

В TRACE v3 используется стратегия **фактов + подсказок**:

1. **Факты**:
   - строки кода;
   - контекст выполнения;
   - время `Total`/`Pure`;
   - блоки `Func/Proc (lines X-Y)`;
   - группировка по `(Module, Context, Extension)`.
2. **Подсказки**:
   - `CALL MAP` с бюджетом вложенных вызовов;
   - эвристическая ссылка `-> see:` на блок из `MODULES`.

## Компоненты

### ProcedureGrouper

- Вход: список событий PFF.
- Группировка по `(Module, Context, Extension)`.
- Разбиение на блоки по маркерам:
  - `КонецФункции` -> `Func`;
  - `КонецПроцедуры` -> `Proc`;
  - иначе `Block`.
- Выход: блоки с `line_start`, `line_end`, `total`, `pure`, списком строк.

### CallMapBuilder

- Вход: события + результат `ProcedureGrouper`.
- Находит строки с заметным бюджетом: `Budget = Total - Pure`.
- Ищет возможный целевой блок по:
  - короткому имени модуля в коде (паттерн `Модуль.Метод(`);
  - близости `Budget` к `Total` блока.
- Формирует опциональные ссылки `-> see:`.

## Интерпретация результатов

- `MODULES` — источник подтвержденных фактов.
- `CALL MAP` — приоритетные кандидаты для анализа цепочки вызовов.
- Любая связь вызовов из `CALL MAP` считается гипотезой до проверки по коду и контексту.
