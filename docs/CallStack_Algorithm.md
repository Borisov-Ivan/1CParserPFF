# Алгоритм восстановления стека вызовов (Call Stack Reconstruction)

Поскольку PFF хранит записи сгруппированными по модулям, а не в хронологическом порядке, для восстановления реального дерева вызовов (Trace) требуется специальный алгоритм.

## Исходные данные

- **FlatRecords**: Список всех записей из PFF.
- **Modules**: Словарь, где ключ — имя модуля, значение — список записей этого модуля.

## Шаг 1: Подготовка данных

1. Загрузить все записи в память.
2. Для каждой записи распарсить `Code` для выявления потенциальных вызовов:
   - `Модуль.Метод()`
   - `Метод()` (вызов внутри того же модуля)
3. Идентифицировать "контейнеры" (процедуры/функции):
   - Группировать последовательные строки модуля в "Процедуры".
   - Границы: от заголовка (или первой строки) до `КонецПроцедуры` / `КонецФункции`.
   - Вычислить суммарное время `Total` и `Pure` для всей процедуры.

## Шаг 2: Построение дерева (Top-Down + Heuristic)

### 2.1 Поиск корней (Roots)
Найти записи, которые вероятнее всего являются точками входа:
- События форм (`ПриСозданииНаСервере`, команды).
- Записи с самым большим `TotalTime` и `Level=0` (в рамках PFF level всегда 0, но мы ищем логический уровень).
- Обычно это обработчики событий в формах или модулях приложений.

### 2.2 Рекурсивное связывание (Matching)

Для каждой записи `Caller`, у которой `TotalTime > PureTime` (есть вложенные вызовы):

1. **Анализ кода:** Определить имя вызываемого метода и модуля из строки кода.
   - *Пример:* `Клиент.ВыполнитьКлиентскийКод()` -> Ищем модуль `ОбщийМодуль.Клиент` (или похожий) и метод `ВыполнитьКлиентскийКод`.

2. **Поиск кандидата (Callee):**
   - Искать среди "Процедур" (см. Шаг 1) подходящего модуля.
   - **Критерий времени:** `Callee.TotalTime` ≈ `Caller.TotalTime - Caller.PureTime`.
     - Допуск (epsilon) важен, так как время может немного отличаться (накладные расходы).
   - **Критерий количества:** `Callee.Count` ≈ `Caller.Count` (если вызов в цикле, PFF может схлопывать или нет).

3. **Обработка переходов C -> S:**
   - Если `Caller` имеет флаг `SrvProcFlag=1` (Клиент вызывает Сервер):
     - Искать Callee **в другом блоке** (Серверном).
     - Имя модуля и метода то же самое, но контекст — Сервер.

4. **Обработка Расширений:**
   - Если вызван метод, который перехвачен расширением (`&Вместо`):
     - В PFF будет запись из модуля Расширения.
     - Необходимо искать Callee среди расширений данного модуля.

### 2.3 Упорядочивание (Ordering)

После того как для `Caller` найдены все `Callee` (если их несколько в одной строке — сложно, но обычно 1 строка = 1 вызов):
- Если в процедуре несколько вызовов, их порядок определяется порядком строк в `Caller`.

## Шаг 3: Сборка итогового Trace

Обход построенного дерева (DFS) для генерации плоского списка событий в хронологическом порядке с проставленными `Level`.

1. `Level = 0`.
2. Печать `Caller`.
3. `Level += 1`.
4. Печать `Callee` (рекурсивно).
5. `Level -= 1`.

## Эвристики для сложных случаев

- **Не удалось определить модуль по коду:**
  - Искать среди всех модулей процедуру с подходящим именем и подходящим `TotalTime`.
- **Рекурсия:**
  - Отслеживать глубину стека, чтобы не зациклиться.
- **Динамические вызовы:** (`Выполнить`, `Вычислить`) — практически невозможно восстановить статически, только по совпадению времени "сиротских" процедур.

## Ограничения

- Алгоритм полагается на точность замеров времени. Если `PureTime` замерено неверно, дерево может быть построено с ошибками.
- Одинаковые вызовы в цикле могут быть сложны для разнесения (какой вызов к какой итерации относится), но для агрегированного отчета это не критично.
