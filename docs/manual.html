1. О программе

1CParserPFF — инструмент для анализа файлов замеров производительности 1С (расширение .pff). Он преобразует сырые, трудночитаемые данные замера в структурированные текстовые отчеты, удобные как для разработчиков, так и для анализа с помощью LLM (языковых моделей).

Программа написана на Python 3 и использует библиотеку tkinter для графического интерфейса. Она не требует установки внешних зависимостей.

2. Быстрый старт (GUI)

  1. Запустите файл src/pff_parser_gui.py (или исполняемый файл, если он собран).
  2. Нажмите кнопку «...» в поле «Путь к файлу» и выберите ваш файл замера (.pff или .txt).
  3. Выберите режим работы:
    • Трассировка (TRACE) — если нужно понять логику работы и последовательность вызовов.
    • Производительность (PERF) — если нужно найти узкие места и понять, почему операция выполняется долго.
  4. (Опционально) Настройте другие параметры (см. раздел Настройки GUI).
  5. Нажмите кнопку «Сформировать» (или клавишу Enter).
  6. Результат появится в текстовом поле. Также отчет будет автоматически сохранен в файл рядом с исходным замером (с суффиксом _TRACE.txt или _PERF.txt).

3. Как получить PFF-файл в 1С

Для получения замера производительности в режиме Предприятия:

  1. Откройте меню Сервис и настройки (или «Главное меню»).
  2. Перейдите в Настройки → Замер производительности.
  3. Нажмите кнопку «Начать замер» (или сочетание клавиш, если настроено).
  4. Выполните действия в программе, которые вы хотите проанализировать (провести документ, открыть форму и т.д.).
  5. Нажмите кнопку «Остановить замер».
  6. В открывшемся окне с результатами замера нажмите кнопку «Сохранить...» (значок дискеты).
  7. Выберите тип файла PFF (Performance File Format) и сохраните его на диск.

4. Два режима работы

TRACE — «Что произошло?»

Этот режим предназначен для восстановления потока выполнения и отладки логики.

Секции отчёта:

  • EXECUTION FLOW — Хронологическое дерево вызовов. Реконструируется эвристически (точность ~90%).
    • Показывает вложенность вызовов.
    • Сворачивает длинные цепочки асинхронных колбэков (например, ВыполнитьОбработкуОповещения).
  • CALL MAP — Список строк, имеющих наибольший Budget (время, потраченное во вложенных вызовах).
    • Содержит ссылки -> see:, указывающие на возможные вызываемые блоки кода в секции MODULES.
  • MODULES — Справочник модулей с детальной информацией.
    • Группировка по модулям и контексту.
    • Тривиальные процедуры (с малым временем) сворачиваются.
    • Структурный шум (КонецЕсли, КонецЦикла) убирается.
    • Повторяющиеся строки схлопываются (30× Реквизиты.Вставить(...)).

PERF — «Почему медленно?»

Этот режим предназначен для поиска проблем производительности и оптимизации.

Секции отчёта:

  • TOP ISSUES — Ранжированный список проблем производительности.
    • Генерируется для форматов замера 2b/2c (где нет явного уровня вложенности).
    • Классифицирует проблемы по типу: HTTP, SQL, Бизнес-логика, Ресурсы, Колбэк.
    • Для каждой проблемы строится цепочка вызовов от корня до узкого места.
  • Дерево критического пути — Классическое дерево вызовов (только для формата 1, где есть поле Level).
  • HOTSPOTS — Топ строк кода по чистому времени (Self time). Показывает самые "тяжелые" строки, которые потребляют процессорное время сами по себе, а не ожидают вложенных вызовов.

5. Словарь терминов

Термин Значение
Total (мс) Полное время выполнения строки, включая время всех вызванных из неё процедур и функций.
Pure / Self (мс) Чистое время, потраченное именно на выполнение кода этой строки (без учёта вложенных вызовов).
Budget Total - Pure. Время, "потраченное" на вложенные вызовы. Используется для поиска того, кого вызвала эта строка.
[C] Код выполняется на Клиенте.
[S] Код выполняется на Сервере.
[C→S] Момент вызова серверной процедуры с клиента (переход контекста).
[?] Контекст выполнения не удалось определить однозначно.
[Ext:Имя] Код выполняется в Расширении конфигурации с указанным именем.
★ Маркер узкого места в дереве (строка с высоким Self-временем).
⤷ [колбэки ×N: ...] Свёрнутая цепочка асинхронных обработчиков оповещений (технические вызовы платформы).
[свёрнуто] Процедура заняла слишком мало времени (меньше порога), её детали скрыты для компактности.
Count Количество выполнений строки. Если > 1, значит платформа агрегировала несколько вызовов в одну запись.

6. Настройки GUI

  • Путь к файлу: Выберите исходный файл .pff или .txt.
  • Режим: Переключение между TRACE и PERF (см. раздел 4).
  • Точка входа: Фильтр. Можно ввести Модуль:Строка или часть кода (например, ПриСозданииНаСервере). Парсер покажет только тот блок сеанса (сессию), в котором встретилась эта строка.
  • Порог (мс): Минимальное время (Total), чтобы событие попало в отчет.
    • В режиме PERF: настраивается вручную. По умолчанию 1% от общего времени.
    • В режиме TRACE: поле недоступно (используется автоматический расчет для фильтрации шума).
  • Разворачивать имена модулей:
    • Включено: В отчете пишутся полные имена модулей (например, ОбщийМодуль.РаботаСЭП.Модуль).
    • Выключено: Имена заменяются на короткие алиасы (M1, M2...), а в конце отчета добавляется таблица расшифровки. Полезно для уменьшения размера файла.
  • Умное сжатие (только TRACE): Объединяет строки кода, перенесенные на новую строку, в одну логическую запись.
  • Промпт для модели: Добавляет в начало отчета специальный блок текста с инструкцией для LLM (ChatGPT, Claude и др.), объясняющий формат данных. Рекомендуется оставлять включенным, если вы планируете анализировать отчет с помощью ИИ.

7. Командная строка (CLI)

Вы можете использовать парсер из консоли для автоматизации.

python src/pff_parser.py [file] [output] [options]

Аргументы:

  • file — путь к PFF-файлу (обязательный).
  • output — путь к выходному файлу (опциональный).
  • --mode {TRACE,PERF} — режим работы.
  • --threshold N — порог значимости в мс.
  • --entry "Module:Line" — точка входа (фильтр по строке).
  • --main-block N — обработать только блок с индексом N (0, 1, 2...).
  • --no-compact — отключить умное сжатие строк.
  • --no-context — не показывать метки контекста [C]/[S].
  • --no-expand-modules — использовать короткие имена модулей (M1, M2).
  • --no-model-prompt — не добавлять инструкцию для LLM.

Примеры:

# Генерация TRACE отчета
python src/pff_parser.py data/trace.pff

# Генерация PERF отчета с порогом 10 мс
python src/pff_parser.py data/trace.pff --mode PERF --threshold 10

# Анализ конкретного сеанса (блока 0)
python src/pff_parser.py data/trace.pff --main-block 0

8. Формат PFF — техническая справка

Файл PFF — это текстовая сериализация внутренних структур платформы 1С.

  • Общая структура: {Version, SessionCount, MeasurementGUID, SessionBlock1, ...}.
  • Session Block: Описывает сеанс (Клиент, Сервер, Фоновое задание).
  • Запись замера: Содержит 19 полей, включая:
    • Module, Line, Code — где и что выполнялось.
    • TotalTime, PureTime — время.
    • Count — количество вызовов (агрегация).
    • Флаги контекста (Клиент, Сервер).
    • Информацию о Расширении (GUID, имя).
Важно: В файле PFF (форматы 2b/2c) записи сгруппированы по модулям, а не хронологически. Поле Level (уровень вложенности) обычно отсутствует (равно 0). Это делает восстановление точного дерева вызовов нетривиальной задачей.

9. Алгоритмы парсера

Для превращения "плоского" списка событий в дерево используются следующие алгоритмы:

  • PFFStreamParser: Потоковый парсер, читает файл посимвольно, что позволяет обрабатывать файлы любого размера без загрузки всего содержимого в память.
  • ProcedureGrouper: Группирует события по модулям, контексту и расширениям. Разбивает поток на логические блоки (Процедуры/Функции) по маркерам КонецПроцедуры / КонецФункции.
  • CallMapBuilder: Анализирует разницу Total - Pure (Budget). Если бюджет велик, значит, строка вызывала другие процедуры. Алгоритм ищет подходящие блоки кода, время выполнения которых совпадает с бюджетом.
  • ExecutionFlowBuilder: Рекурсивно восстанавливает дерево вызовов, сопоставляя вызовы (по коду и бюджету) с имеющимися блоками процедур. Также сворачивает цепочки колбэков.
  • IssueAnalyzer: Используется в режиме PERF. Кластеризует "горячие точки" (Hotspots) по модулям, классифицирует их (SQL, HTTP и т.д.) и строит для них "обратное дерево" (кто это вызвал), чтобы показать контекст проблемы.

10. Ограничения и точность

  • Эвристическая природа: Так как в PFF (2b/2c) нет явных связей "родитель-потомок", дерево восстанавливается с точностью ~85-90%. Возможны ошибки в определении вложенности, особенно если несколько процедур имеют одинаковое время выполнения.
  • Агрегация (Count > 1): Если платформа свернула несколько вызовов одной строки в одну запись (Count > 1), хронология теряется. Парсер пытается учесть это, но точность снижается.
  • Факты vs Гипотезы:
    • Секция MODULES содержит 100% факты из файла замера.
    • Секция EXECUTION FLOW и TOP ISSUES содержат гипотезы о связях вызовов.
