# TRACE v6 Plan (после ревью): Full / Normal / Compact

## 0. Итог ревью v5 и ценность для LLM
Фокус ревью: ценность для модели, которая уже видит полный текст модуля и использует TRACE для объяснения поведения.

Высокая ценность (оставить и реализовать в первую очередь):

- фиксированные режимы `full/normal/compact`,
- прозрачность скрытий (`TRACE COVERAGE`),
- явный режим в заголовке отчета и в заголовке промпта,
- запрет хардкода по именам модулей/расширений.

Средняя ценность (реализовать после ядра):

- замена чекбокса `Умное сжатие` на селектор детализации в GUI,
- legacy-совместимость `--no-compact`.

Недостатки v5 (добавить в v6, иначе модель теряет качество вывода):

- не было явного разделения между служебными метриками подготовки отчета и метриками, которые показываются пользователю в TRACE,
- нет стабильных идентификаторов событий и сквозных ссылок между секциями,
- нет маркировки достоверности (где факт, где эвристика),
- нет воспроизводимой подсказки "как получить тот же кейс в `TRACE FULL` одной командой",
- критерии приемки и проверки слишком ручные, мало автоматических инвариантов.

## 1. Цель
Сделать TRACE-отчет управляемым по детализации без потери причинно-следственной ценности для анализа поведения.

Результат должен позволять модели:

- связать выводы с конкретными строками модулей,
- отделять подтвержденные факты от эвристических связей,
- быстро эскалировать из `normal/compact` в `full` без потери контекста фильтров.

Ограничение: TRACE не используется для оценки производительности по времени; это зона режима `PERF`.

## 2. Принципы проектирования (model-first)

1. Доказуемость: каждый важный вывод опирается на конкретные `Module:Line` и/или `EventID`.
2. Прозрачность: для не-`full` всегда видно, что скрыто, сколько скрыто и почему.
3. Воспроизводимость: отчет содержит команду/параметры для повторного запуска.
4. Детерминизм: одинаковый вход и параметры дают одинаковый порядок и формат секций.
5. Непрерывность: `full` >= `normal` >= `compact` по полноте фактов.
6. Разделение режимов: временные оценки и выводы о производительности формируются в `PERF`, не в TRACE.

## 3. Семантика режимов TRACE

### `full`
Назначение:

- финальная диагностика причин поведения,
- выбор точек изменения в коде.

Требования:

- минимальная фильтрация,
- без агрессивного коллапса повторов и callback-цепочек (или с явной маркировкой свертки),
- `CALL MAP` не обрезается скрыто; если есть технический лимит, он явно отражается в `TRACE COVERAGE`.

### `normal` (default)
Назначение:

- основной рабочий режим анализа.

Требования:

- сохраняет ключевую причинно-следственную цепочку,
- умеренная фильтрация шума,
- обязательны метрики скрытия (временные KPI в TRACE не публикуются).

### `compact`
Назначение:

- быстрый triage и сравнение прогонов.

Требования:

- агрессивная фильтрация и сжатие,
- обязательная явная отчетность о потерях,
- обязательная рекомендация эскалации в `full` при недостатке данных.

## 4. Обязательная структура TRACE-отчета

### 4.1. Заголовок режима

- `=== TRACE [FULL] ===`
- `=== TRACE [NORMAL] ===`
- `=== TRACE [COMPACT] ===`

### 4.2. `TRACE META` (новое, обязательно)
Минимум:

- `mode`,
- `entry/main-block` (если применялись),
- `trace_detail`,
- версия формата (`TRACE v6`),
- флаги фильтрации/коллапса.

### 4.3. `TRACE COVERAGE` (для пользователя, усилено)
Минимум метрик:

- `events_total`, `events_shown`, `events_hidden`,
- `call_map_total_entries`, `call_map_shown_entries`, `call_map_hidden_entries`,
- `modules_total_events`, `modules_shown_events`, `modules_hidden_events`,
- причины скрытия с количеством:
- `structural_noise`,
- `control_leaf_noise`,
- `terminal_trivial`,
- `tiny_leaf`,
- `collapsed_repeats`,
- `collapsed_callbacks`,
- `threshold_hidden`.

### 4.4. Служебные метрики подготовки TRACE (внутренние, не показывать в отчете)
Используются только внутри алгоритма формирования отчета/сжатия:

- `time_total_ms`, `time_shown_ms`, `time_hidden_ms`,
- `time_coverage_pct`,
- `call_map_budget_total_ms`, `call_map_budget_shown_ms`, `call_map_budget_coverage_pct`,
- иные служебные пороги/бюджеты фильтрации.

Правило:

- эти метрики не являются пользовательскими параметрами TRACE,
- эти метрики не являются целевыми метриками приемки TRACE,
- для анализа времени и производительности использовать `PERF`.

### 4.5. Сквозные ссылки и идентификаторы (новое, обязательно)

- каждое показанное событие имеет стабильный `EventID` в рамках отчета, например `E12345`,
- `EXECUTION FLOW`, `CALL MAP`, `MODULES` ссылаются на один и тот же `EventID`,
- формат ссылок человекочитаемый: `E12345 -> ModuleName:Line`.

### 4.6. Маркировка достоверности (новое, обязательно)

- для фактов: `FACT`,
- для эвристических связей: `INFERRED`.

Пример применения:

- в `EXECUTION FLOW` связь вызова, восстановленная эвристикой, помечается `INFERRED`,
- строки `MODULES` и `CALL MAP`, подтверждаемые исходными данными трассы, помечаются `FACT`.

### 4.7. `TRACE REPRODUCE` (новое, обязательно)
Короткий блок с готовой командой:

- как получить этот же отчет повторно,
- как получить этот же срез в `TRACE FULL`.

## 5. Требования к промпту модели

### Заголовок промпта

- `=== ПРОМПТ ДЛЯ МОДЕЛИ (TRACE FULL) ===`
- `=== ПРОМПТ ДЛЯ МОДЕЛИ (TRACE NORMAL) ===`
- `=== ПРОМПТ ДЛЯ МОДЕЛИ (TRACE COMPACT) ===`

### Обязательные инструкции

- явно указывать текущий режим и его ограничения,
- требовать ссылаться на `EventID` и `Module:Line` в выводах,
- требовать разделять `FACT` и `INFERRED`,
- в `NORMAL` и `COMPACT`: явная инструкция эскалации в `TRACE FULL`,
- в `FULL`: напоминание про локализацию через `entry/main-block`,
- не использовать TRACE для количественной оценки времени; при такой задаче запрашивать `PERF`.

## 6. Решение по "Умное сжатие"
Отдельный чекбокс `Умное сжатие` в TRACE убрать из пользовательского UX.

Вместо него:

- `Детализация TRACE: Full / Normal / Compact`.

Совместимость:

- `--no-compact` оставить как deprecated alias -> `--trace-detail full`,
- при конфликте параметров показывать явное предупреждение.

## 7. План реализации (приоритизация)

### P0 (ядро ценности для LLM)

1. Ввести единый `trace_detail` в API:
   - `process_pff(..., trace_detail=...)`,
   - `ReportGenerator(..., trace_detail=...)`,
   - единый enum/константы: `TRACE_FULL`, `TRACE_NORMAL`, `TRACE_COMPACT`.
2. Реализовать профили фильтрации для трех режимов без хардкода модулей.
3. Добавить режим в заголовки отчета и промпта.
4. Реализовать `TRACE COVERAGE` (пользовательские счетчики скрытия) и внутренний расчет служебных time/budget-метрик только для подготовки отчета.
5. Добавить CLI `--trace-detail {full,normal,compact}` (default `normal`).
6. Сохранить совместимость с `--no-compact` как deprecated alias.

### P1 (доказуемость и качество reasoning)

1. Ввести стабильные `EventID` и сквозные ссылки между `EXECUTION FLOW` / `CALL MAP` / `MODULES`.
2. Добавить маркировку `FACT` / `INFERRED`.
3. Добавить блок `TRACE REPRODUCE` с готовыми командами.
4. Зафиксировать детерминированный порядок сортировки/вывода секций.

### P2 (UX и документация)

1. Обновить `src/pff_parser_gui.py`:
   - убрать `Умное сжатие`,
   - добавить селектор `trace_detail`,
   - активировать только в TRACE,
   - передавать `trace_detail` в `process_pff`.
2. Обновить `README.md`, `docs/README.md`, `HELP_TEXT`.

## 8. CLI и режим PERF

- `--trace-detail` применим только к `--mode TRACE`,
- временные параметры в CLI/GUI для TRACE не добавлять,
- `--threshold` и иные time-параметры относятся только к `PERF`,
- при `--mode PERF` поведение time-параметров остается текущим и функционально не ломается.

## 9. Проверки

### Автоматические (обязательно)

- `python -m py_compile src/pff_parser.py`,
- регрессионный прогон `TRACE/PERF` на `tests/reference.pff`,
- тест инварианта полноты: `full >= normal >= compact` по:
- `events_shown`,
- `call_map_shown_entries`.
- тест наличия обязательных секций и заголовков режимов,
- тест корректности deprecated-алиаса `--no-compact`,
- тест, что в TRACE не появляются пользовательские time-параметры,
- тест соответствия структуры отчета целевому шаблону из раздела 12 (section order + обязательные маркеры).

### Ручные

- в `normal/compact` виден `TRACE COVERAGE`,
- есть `TRACE REPRODUCE`,
- эскалация в `TRACE FULL` воспроизводит тот же фильтр (`entry/main-block`),
- `normal` не теряет ключевую причинно-следственную цепочку,
- формат реально совпадает с шаблоном раздела 12 на контрольном файле `examples/Проверка расчета хэша_TRACE.txt`.

## 10. Критерии приемки

- режимы `full/normal/compact` реализованы и документированы,
- отчет и промпт всегда содержат явный режим,
- для не-`full` режимов есть прозрачный учет скрытия (количество + причины),
- служебные time/budget coverage используются только внутри подготовки TRACE,
- в TRACE отсутствуют пользовательские временные параметры,
- модель может ссылаться на `EventID` и `Module:Line` для обоснования вывода,
- в отчете есть разделение `FACT` / `INFERRED`,
- `TRACE REPRODUCE` позволяет получить идентичный срез и его `TRACE FULL`-версию,
- GUI использует `trace_detail` вместо отдельного флага `Умное сжатие`,
- поведение универсально и не зависит от имен конкретных модулей/расширений,
- отчет соответствует целевому шаблону раздела 12.

## 12. Шаблон целевого TRACE-отчета (эталон для сверки)
Основание: `examples/Проверка расчета хэша_TRACE.txt`.

Ниже фиксируется целевой порядок и назначение разделов. Это эталон структуры (не буквальная копия всех строк).

```text
[R1] === ОТЧЁТ PFF ===
Назначение: корневой заголовок отчета.

[R2] === СВОДКА ===
Назначение: минимальный контекст прогона.
Ожидаемые поля:
- События: <N>
- Вход: <entry|все>
- Блоки: <перечень Bx>
- Общее время: <справочно, без KPI-интерпретации в TRACE>
- Основная ветвь (L0): <справочно>

[R3] === РАСШИРЕНИЯ ===
Назначение: список подключенных расширений (если есть).

[R4] === ПРОМПТ ДЛЯ МОДЕЛИ (TRACE <MODE>) ===
Назначение: контракт чтения отчета моделью.
Обязательные подпункты:
- структура отчета,
- правила чтения секций,
- интерпретация,
- граница FACT/INFERRED,
- инструкция эскалации в TRACE FULL (для NORMAL/COMPACT).

[R5] === КОНЕЦ ПРОМПТА ===
Назначение: явная граница между инструкциями и данными.

[R6] === TRACE [<MODE>] ===
Назначение: начало тела TRACE.

[R7] === TRACE META ===
Назначение: параметры формирования отчета (mode, entry/main-block, trace_detail, flags).

[R8] === TRACE COVERAGE ===
Назначение: прозрачность скрытий.
Поля:
- events_total / shown / hidden
- call_map_total / shown / hidden
- modules_total / shown / hidden
- причины скрытия с количествами

[R9] === EXECUTION FLOW (эвристическая реконструкция) ===
Назначение: причинно-следственная история выполнения.
Формат узла (пример):
- [контекст] Модуль:Строка | Код [метка FACT/INFERRED]

[R10] === CALL MAP ===
Назначение: карта ключевых узлов цепочки вызовов по budget для навигации.
Формат записи (пример):
- #N [контекст] Модуль:Строка | Budget: ...
- -> see: Модуль [контекст] Func/Proc(:a-b) ...

[R11] === MODULES (справочник модулей) ===
Назначение: подтверждающая построчная детализация по модулям/блокам.
Формат:
- --- Bx [Контекст] ПолноеИмяМодуля ---
- [S/C] Func/Proc(:a-b) Total ... Pure ...
- :Line | Code  Total  Pure

[R12] === TRACE REPRODUCE ===
Назначение: команды повторного запуска:
- этот же отчет,
- этот же срез в TRACE FULL.
```

Правило интерпретации времени в шаблоне:

- временные значения в TRACE допускаются как справочные факты трассы,
- они не являются целевыми параметрами оптимизации и не заменяют PERF-анализ.

## 13. Оценка формата раздела 12 глазами LLM
Оценка текущего шаблона (как формата reasoning по поведению): **8/10**.

Сильные стороны:

- четкая секционность, легко парсится моделью,
- `EXECUTION FLOW` + `MODULES` дают связку "гипотеза -> подтверждение",
- `CALL MAP` быстро выводит на ключевые узлы цепочки вызовов,
- встроенный промпт снижает риск неправильной интерпретации.

Слабые места / риски:

- без `EventID` ссылки между секциями неоднозначны в длинных трассах,
- без явных меток `FACT/INFERRED` модель может смешивать эвристику и факты,
- смешение справочных time-полей TRACE с задачами оптимизации может провоцировать неверный фокус (нужно жестко направлять в PERF),
- при сильной фильтрации без детального `TRACE COVERAGE` растет риск ложной уверенности.

Вывод:

- формат уже пригоден для объяснения поведения,
- после внедрения `EventID`, `FACT/INFERRED`, усиленного `TRACE COVERAGE` и `TRACE REPRODUCE` ожидаем качество **9/10+** для задач root-cause в TRACE.
