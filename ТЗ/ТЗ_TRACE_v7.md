# ТЗ: Оптимизация формата TRACE → v7

> Основание: [ТЗ/анализ.md](анализ.md) — расширенный критический анализ TRACE v6.
> Предыдущий план: [ТЗ/plan.md](plan.md) — TRACE v6 Plan.
> Версия формата: **TRACE v7**.
> Затрагиваемые файлы: `src/pff_parser.py`, `src/pff_parser_gui.py`, `tests/test_trace_v6.py`.
> Документация: `docs/README.md`, `docs/manual.html` — техническая справка по формату PFF.

---

## 0. Цель

Сократить объём TRACE-отчёта на **50-70%** без потери причинно-следственной ценности.
Устранить дублирование между секциями. Сделать формат пригодным для работы с LLM в ограниченном контекстном окне.
Убрать из отчёта конфиденциальные данные (имена хостов).
Упростить пользовательский интерфейс: два режима вместо трёх, без устаревших концепций «блоков» и «точки входа».

### Целевые метрики (на контрольном замере `Проверка расчета хэша.pff`)

| Метрика             | FULL сейчас → цель   | COMPACT сейчас → цель |
|---------------------|----------------------|----------------------|
| Строк               | 833 → **≤500**       | 259 → **≤80**        |
| Символов             | 79 686 → **≤40 000** | 20 665 → **≤6 000**  |
| Overhead (ссылки и т.д.) | 36% → **≤15%**   | 30% → **≤10%**       |

## 1. Принципы

1. **Доказуемость** — вывод опирается на `EventID` + `Module:Line`.
2. **Прозрачность** — что скрыто, сколько, почему.
3. **Воспроизводимость** — TRACE REPRODUCE.
4. **Детерминизм** — одинаковый вход → одинаковый выход.
5. **Непрерывность** — `full ⊇ compact` по полноте.
6. **Разделение** — время → PERF, логика → TRACE.
7. **Экономия токенов** — каждый символ отчёта должен нести информационную ценность. Повторение одних данных в разных формах запрещено.
8. **Фокус на сценарий** — в `compact` показываются только модули, связанные с основной цепочкой выполнения; фоновые процессы отсекаются.
9. **Конфиденциальность** — имена хостов/серверов/клиентских машин НЕ выводятся в отчёт.

## 2. Ключевые решения (контекст для реализатора)

### 2.1. Два режима вместо трёх

Режим `TRACE_NORMAL` **удаляется полностью** — из кода, из GUI, из CLI.

| Что | Было | Стало |
|-----|------|-------|
| CLI `--trace-detail` | `full / normal / compact` | `full / compact` |
| GUI | Выпадающий список 3 варианта | Два radio: `Обзор (compact)` / `Подробный (full)` |
| Код | `TRACE_NORMAL = "normal"` + вся логика | Удалить константу, ветки `if trace_detail == "normal"`, тесты |
| `--no-compact` | Deprecated alias → `full` | Сохранить для обратной совместимости → `full` |

При передаче `--trace-detail normal` в CLI — fallback на `compact` с предупреждением в stderr.

### 2.2. Удаление «блоков» и «точки входа»

Концепции `main_block` и `entry` удаляются из GUI и из отчёта.

**Обоснование:**
- «Блок» — это сессия (Сервер/Клиент). Контекст выполнения (`[C]`, `[S]`, `[C→S]`) уже определяется из **полей каждой записи PFF** (индексы 9=ClientFlag, 10=ServerFlag, 11=SrvProcFlag), а не из заголовка сессионного блока. Блоковая метка `B0 [Сервер]` — пересказ того, что уже известно на уровне событий.
- «Точка входа» — текстовый поиск, который неявно фильтрует до блока. Обман ожиданий: пользователь ждёт фокуса на функцию, а получает весь блок.

| Что | Было | Стало |
|-----|------|-------|
| GUI: поле «Точка входа» | Текстовое поле | **Удалить** |
| GUI: `main_block` | Захардкожен `None` | **Удалить параметр** |
| CLI: `--entry` | Работал | **Удалить аргумент** |
| CLI: `--main-block` | Работал | **Удалить аргумент** |
| Код: `resolve_entry()` | Функция | **Удалить** |
| Код: `filter_by_main_block()` | Функция | **Удалить** |
| Отчёт: `B0 [Сервер]` в заголовках MODULES | Каждый модуль | **Убрать полностью** |
| Отчёт: `main_block: all` в META | Строка | **Убрать** |
| Отчёт: `entry: all` в META | Строка | **Убрать** |
| СВОДКА: `Блоки: B0: 1360 соб., Сервер (host)` | Подробно | Только `Сессии: 2 (Сервер, Тонкий клиент)` — без хостов, без счётчиков |

Парсер по-прежнему читает `session_info` для корректного определения контекста, но **не выводит** блоковые метки в отчёт.

### 2.3. Конфиденциальность: без хостнеймов

Имена хостов (`host` из `session_info`) **нигде не выводятся** в отчёт:
- Убрать из СВОДКИ (`Сервер (sr-dc-0475.corp.gidroogk.com)` → просто `Сервер`).
- Убрать из TRACE META.
- Убрать из TRACE REPRODUCE.
- Убрать из PERF (если были).

### 2.4. Контекст выполнения — из полей записи

Контекст `[C]`/`[S]`/`[C→S]` определяется из полей каждой записи PFF:

| Поля (Client, Server, SrvProc) | Контекст |
|-------------------------------|----------|
| `(1, 0, 0)` | `[C]` — Клиент |
| `(0, 1, 0)` | `[S]` — Сервер |
| `(1, 0, 1)` | `[C→S]` — Вызов сервера с клиента |

Это **уже реализовано** в `_context_from_three_fields()`. Контекст остаётся в отчёте как и прежде (`[C]`, `[S]`, `[C→S]`). Удаляются только блоковые метки `B0`/`B1`.

## 3. Задачи (приоритизированы по impact)

### T1. [P0 CRITICAL] Таблица алиасов модулей — секция MODULES MAP

**Что:** Новая обязательная секция, размещается между TRACE COVERAGE и EXECUTION FLOW.

**Формат:**
```
=== MODULES MAP ===
M01: [X1] Обработка.НастройкаПрограммы.Форма.НастройкиЭлектронныхПодписей.Форма
M02: [X1] ОМ.ргСервисКриптографииCryptoAPI
M03: [X1] ОМ.ргСервисКриптографииОбщегоНазначения
M04: ОМ.ОбщегоНазначения
M05: ОМ.ВнешниеКомпонентыСлужебный
M06: ОМ.ВнешниеКомпонентыСлужебныйВызовСервера
M07: Справочник.ВнешниеКомпоненты.МодульМенеджера
M08: ОМ.ОбщийОбработчикОжиданияГлобальный
X1: ргОблачныеПодписиKonturCryptoAPI
```

**Правила:**
- `ОМ.` — стандартное сокращение для `ОбщийМодуль.` (самый частый тип).
- `X<N>` — алиасы расширений, расшифровка в конце MAP.
- Алиасы `M<NN>` назначаются в порядке появления в отчёте.
- Во всех последующих секциях (FLOW, CALL INDEX, MODULES) используется `M01:32` вместо полного пути.

**Где реализовать:** `ReportGenerator.generate_trace()` — формировать словарь `module_aliases` при проходе по данным, генерировать секцию перед FLOW.

**Ожидаемый эффект:** устранение ~30% overhead за счёт исключения повторения полных путей.

### T2. [P0 CRITICAL] Компактные ссылки EventID

**Что:** Заменить формат `[FACT E01534 -> FullPath:Line]` на `#1534`.

**Текущий формат (~125 символов):**
```
[FACT E01534 -> ргОблачныеПодписиKonturCryptoAPI Обработка.НастройкаПрограммы.Форма.НастройкиЭлектронныхПодписей.Форма:32]
```

**Целевой формат (5 символов):**
```
#1534
```

**Соглашения:**
- `#` — факт (FACT). Дефолт для секций MODULES и CALL INDEX.
- `?` — эвристика (INFERRED). Дефолт для секции EXECUTION FLOW.
- Дефолтный тип указывается один раз в заголовке секции. Помечаются только **исключения**.
- Номер EventID без ведущих нулей и без префикса `E` (экономия 2 символа на каждом).
- Путь модуля НЕ дублируется в ссылке — восстанавливается из MODULES MAP.

**Пример строки EXECUTION FLOW (было / стало):**
```
Было: [INFERRED E01354 -> ...Форма:47] [S] Форма:47 | Хеш = ВычислитьХешГОСТ2012(ДвоичныеДанные);  [1552ms / 23ms]

Стало: ?1354 [S] M01:47 | Хеш = ВычислитьХешГОСТ2012(ДвоичныеДанные);
```
Было ~210 символов, стало ~60 символов. **Экономия 71% на строку.**

**Где реализовать:** Функция форматирования EventID-ссылок (сейчас в `_fmt_eid_ref` или inline). Заменить на `_compact_eid(eid, is_default_type)`.

### T3. [P0 CRITICAL] Убрать время из TRACE

**Что:** Удалить все временные метрики из TRACE-отчёта.

**Удалить:**

| Секция | Что убрать | Пример |
|--------|-----------|--------|
| EXECUTION FLOW | `[Self: 32ms]`, `[1552ms / 23ms]` | Хвост каждой строки |
| CALL MAP / CALL INDEX | `Budget: 1552.05ms`, `[Total: 1528.05ms]` | — |
| MODULES заголовки процедур | `Total: 0.62ms Pure: 0.52ms` | Заголовок `[S] Proc (:19-305)` |
| MODULES строки событий | Две правые колонки `0.013  0.013` | Каждая строка кода |

**Исключение (только для FULL):** В заголовке процедуры MODULES оставить `Total` с пометкой `(ref)` — справочное значение для навигации:
```
  [S] Func (:4357-4423) Total: 1528ms (ref)
```

**Обоснование:** Принцип 6: «временные оценки — зона PERF, не TRACE». Текущий отчёт нарушает этот принцип 544 раза (в FULL).

**Где реализовать:** `_generate_modules_section()`, `_generate_flow_section()`, `_generate_call_map()`.

### T4. [P1 HIGH] CALL MAP → CALL INDEX

**Что:** Заменить многострочную секцию CALL MAP (до 120 строк в FULL) на компактный навигационный индекс.

**Текущий CALL MAP (30 записей × 3-4 строки = ~120 строк):**
```
#1 [FACT E01534 -> ...Форма:32] [C→S] Форма:32 | Budget: 1552.05ms
   Результат = ргргПроверитьПолучениеХэшаНаСервере();

#2 [FACT E01354 -> ...Форма:47] [S] Форма:47 | Budget: 1528.05ms
   Хеш = ргСервисКриптографииCryptoAPI.ВычислитьХешГОСТ2012(ДвоичныеДанные);
   -> [INFERRED] see: ргСервисКриптографииCryptoAPI [S] Func(:4357-4423) [Total: 1528.05ms]
```

**Целевой CALL INDEX (5-10 строк):**
```
=== CALL INDEX ===
Навигация по ключевым узлам цепочки вызовов (подробности в MODULES).

#1534 [C→S] M01:32 Результат = ргргПроверитьПолучениеХэшаНаСервере()
  → #1354 [S] M01:47 → #1303 M02:4363 → #1293 M03:35 → #761 M04:6468 → #766 M04:6476
#775 [S] M04:6646 ПодключитьВнешнююКомпоненту (leaf)
#1497 [C→S] M08:25 ОбщийОбработчикОжидания (фон)
```

**Правила:**
- Главная цепочка развёрнута как дерево стрелок `→`.
- Leaf-узлы (самостоятельное время) помечаются `(leaf)`.
- Фоновые ветки — одной строкой с пометкой `(фон)`.
- Без Budget/Total — это TRACE, не PERF.
- В COMPACT: показывать только главную цепочку.

**Где реализовать:** Новый метод `_generate_call_index()` вместо `_generate_call_map()` при `mode == TRACE`.

### T5. [P1 HIGH] Убрать строки `[свёрнуто по threshold]`

**Что:** Полностью убрать строки-заглушки о скрытых функциях.

**Текущее поведение:** В MODULES для каждой скрытой функции выводится:
```
  [S] Func (:1846-1853) Total: 0.02ms  [свёрнуто по threshold]
```
Таких строк десятки. Каждая ~70 символов = **2-3 КБ мусора**.

**Целевое поведение:**

| Режим | Что делать |
|-------|-----------|
| COMPACT | **Не показывать** ни скрытые функции, ни модули, состоящие только из скрытых функций |
| FULL | Одна строка-сводка на группу: `[+ 15 функций, Total < 0.1ms]` |

**Обоснование:** Факт скрытия уже зафиксирован в TRACE COVERAGE (`threshold_hidden=N`). Поштучное перечисление дублирует COVERAGE.

**Где реализовать:** `_generate_modules_section()` — условие на `self.trace_detail`.

### T6. [P1 HIGH] Фильтрация фоновых модулей в COMPACT

**Что:** В режиме COMPACT показывать в MODULES только модули, связанные с основной цепочкой выполнения (EXECUTION FLOW).

**Логика:**
1. Собрать множество модулей, фигурирующих в EXECUTION FLOW (`flow_modules`).
2. COMPACT: `MODULES` показывает **только** `flow_modules`.
3. FULL: показывает всё (текущее поведение).

**Конкретно для контрольного замера** из COMPACT уходят:
- ОбщийОбработчикОжиданияВызовСервера (фоновый таймер)
- РаботаСУведомлениями (уведомления)
- ВстроеннаяПочтаСервер (почта)
- Сотрудники (справочник сотрудников)
- РаботаСФайламиВызовСервера (файлы)
- РаботаСВиджетамиКлиент (виджеты)
- РезервноеКопированиеИБКлиент (бекап)

**Где реализовать:** `_generate_modules_section()` — фильтр по `flow_modules` set.

### T7. [P1 HIGH] Имена выходных файлов с учётом режима

**Что:** Имя выходного файла должно отражать и mode, и trace_detail.

**Текущее поведение:**

| Компонент | Текущее | Проблема |
|-----------|---------|----------|
| GUI `get_save_path()` | `base + "_TRACE.txt"` | Не различает full/compact |
| CLI (без -o) | `PFF_Report.txt` | Не содержит ни mode, ни detail |

**Целевое поведение:**

| Mode | trace_detail | Имя файла |
|------|-------------|-----------|
| TRACE | full | `{base}_TRACE_FULL.txt` |
| TRACE | compact | `{base}_TRACE_COMPACT.txt` |
| PERF | — | `{base}_PERF.txt` |

**Где реализовать:**

1. **GUI** (`src/pff_parser_gui.py`):
```python
def get_save_path(file_path: str, mode: str, trace_detail: str = None) -> str:
    base = os.path.splitext(file_path)[0]
    if mode == "TRACE" and trace_detail:
        suffix = f"_TRACE_{trace_detail.upper()}"
    else:
        suffix = "_PERF"
    return base + suffix + ".txt"
```

2. **CLI** (`src/pff_parser.py`, блок `main()`):
   - Если `args.output` не указан, формировать путь по тому же правилу:
     `{dir}/{basename}_TRACE_{DETAIL}.txt` или `{dir}/{basename}_PERF.txt`.
   - Если `args.output` указан — использовать как есть.

## 6. Эталонная справка GUI (HELP_TEXT)

Это **точный текст**, который должен быть установлен в `HELP_TEXT` в `pff_parser_gui.py`:

```
=== Руководство 1CParserPFF ===

1. НАЗНАЧЕНИЕ
1CParserPFF анализирует файлы замеров производительности 1С (.pff)
и формирует текстовые отчёты для разбора разработчиком или
языковой моделью (LLM).

2. ДВА ТИПА АНАЛИЗА

  TRACE — «Что произошло?»
  Восстанавливает цепочку вызовов: какой код выполнялся,
  в каком порядке и с каким контекстом ([C] клиент, [S] сервер).
  Используйте когда нужно понять логику выполнения,
  найти причину ошибки, проверить какой код вызывался.

  PERF — «Почему медленно?»
  Находит узкие места по времени: TOP проблем, горячие строки.
  Используйте когда нужно оптимизировать время выполнения.

3. РЕЖИМЫ TRACE

  Обзор (compact) — режим по умолчанию.
  Основная цепочка вызовов, только ключевые модули.
  Достаточно для первого анализа.
  Если информации не хватает — переключитесь на Подробный.

  Подробный (full) — все модули, все события.
  Для глубокого root-cause анализа когда Обзор недостаточен.

4. КАК РАБОТАТЬ
  1. Откройте файл замера (.pff)
  2. Нажмите «Сформировать» (по умолчанию — TRACE Обзор)
  3. Изучите EXECUTION FLOW — это цепочка вызовов
  4. Если нужны детали — переключите на «Подробный»
     и сформируйте заново
  5. Для анализа производительности — выберите PERF

5. ЧТЕНИЕ ОТЧЁТА TRACE
  MODULES MAP — расшифровка алиасов (M01, M02...)
  EXECUTION FLOW — дерево вызовов
    ? = эвристическая связь, # = подтверждённый факт
  CALL INDEX — навигационная цепочка ключевых узлов
  MODULES — детализация по модулям и процедурам
  TRACE COVERAGE — что скрыто и почему
  TRACE REPRODUCE — команда для повторного запуска

6. ПАРАМЕТРЫ
  Порог (мс) — минимальное время для включения
    в отчёт (только для режима PERF)
  Промпт для модели — блок инструкций для LLM
    в начале отчёта (по умолчанию включён)

7. ВЫХОДНОЙ ФАЙЛ
  Результат сохраняется рядом с исходным файлом:
    *_TRACE_COMPACT.txt / *_TRACE_FULL.txt / *_PERF.txt
```

| G02 | `--no-compact` работает как `--trace-detail full` | Тест CLI |
| G03 | `--no-expand-modules` → deprecated no-op, предупреждение в stderr | Тест CLI |
| G04 | `--trace-detail normal` → fallback compact + предупреждение | Тест CLI |
| G05 | Все существующие тесты проходят или обновлены | `python -m unittest discover` |

### 8.8. Структура секций

| # | Критерий | Проверка |
|---|----------|----------|
| H01 | MODULES MAP содержит сокращение `ОМ.` вместо `ОбщийМодуль.` | Grep |
| H02 | MODULES MAP содержит алиасы расширений `X<N>` | Grep |
| H03 | CALL INDEX — **компактный** (≤10 строк для контрольного замера) | Подсчёт |
| H04 | CALL INDEX содержит стрелки `→` для навигации | Grep |
| H05 | TRACE META содержит **ровно**: `format`, `detail`, `sessions` | Grep |
| H06 | TRACE COVERAGE — в формате `shown/total` (без отдельных `events_hidden`) | Grep |
| H07 | TRACE REPRODUCE содержит пороги (`flow_threshold_ms`, `modules_threshold_ms`) | Grep |

## 9. Чего НЕ делать

- **Не трогать PERF** — это ТЗ только для TRACE.
- **Не хардкодить имена модулей/расширений** — алиасы формируются динамически.
- **Не удалять EventID** — они остаются, меняется только формат записи.
- **Не удалять `block_id` из парсера** — внутренний атрибут события, может использоваться для группировки. Удаляется только отображение в отчёте.
- **Не удалять `session_info` из парсера** — используется для строки `sessions:` в META.
- **Не выводить хостнеймы** — ни в какой секции.
- **Не сохранять NORMAL** — удалить полностью, при запросе через CLI → fallback на compact.
